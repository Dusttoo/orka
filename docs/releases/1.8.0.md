# Orka 1.8.0

Orka 1.8.0 lets a host raise the compiled budget hard caps for one repository
with a standing, root-owned policy, so large sprints no longer need a per-ticket
grant for every ticket.

Upgrade notes:

- Re-run `sudo scripts/install-operator-authority.sh <runtime-user>` to add the
  read-only `budget-policy` command to the runtime sudo rule and create the
  private `policies` directory. Until then `validate-config` warns that the
  policy is unavailable and the compiled caps apply.
- Repositories without a policy behave exactly as in 1.7.0.

## Host budget policy

- New root-only `set-budget-policy`, `show-budget-policy`, and
  `clear-budget-policy` commands in the host authority store one standing policy
  per resolved repository path. The runtime can only read it through
  `budget-policy`.
- A policy may raise `max_usd_per_run`, `max_usd_per_ticket`,
  `max_usd_per_sprint`, `pause_usd_per_ticket`, the design, implementation,
  code-review, and security-review phase envelopes,
  `max_model_runs_per_ticket`, `max_reviewer_runs_per_ticket`, and
  `max_usd_without_progress`. Dollar caps are decimal strings up to 100000;
  run counts are integers up to 1000.
- A policy only raises a compiled cap. `.orchestration/config.yaml` still
  chooses values within the caps, and omitted values keep their defaults. When
  the ticket ceiling is raised, an omitted pause defaults to 75% of it within
  the pause cap, and an omitted warning to half the pause.
- API runs, native gateways, the sprint controller's breakers, and the ledger's
  phase clamp all resolve caps for the same repository, so admission never uses
  a cap the policy does not allow.
- A policy that cannot be read falls back to the compiled caps, which can only
  lower spend. `validate-config` prints the reason or a `NOTE` naming the active
  policy, and captain preflight reports `budget_policy`.
