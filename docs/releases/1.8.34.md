# Orka 1.8.34

Orka 1.8.34 routes the production Codex desktop, Claude desktop, and direct
API worker lifecycles through the accepted `orka.execution-backend/v1`
boundary.

## What changed

- Negotiates mandatory execution and containment capabilities before a ticket
  reservation or provider submission.
- Uses one backend lifecycle for launch, attach, heartbeat, progress,
  inspection, cancellation, and terminal evidence across all current routes.
- Adds event-store migration 0004 with permanent, full-identity execution-key
  tombstones written before launch and supervisor-owned lifecycle receipts.
- Preserves the 1.8.33 read-only startup diagnosis, checked database identity,
  and durable writer-lock admission path while extending the authoritative
  store.
- Restores exact launch and terminal receipts after restart without launching
  a duplicate execution, and rejects changed backend, fence, execution-unit,
  worktree, or envelope evidence.
- Keeps cancellation acknowledgements and supervisor fences as separate
  receipts, preserves cancelling state across later observations, and fences
  workers that exit with missing or invalid terminal results.
- Consumes controller attach capabilities without persisting their bearer
  values; durable backend handles contain only opaque digests.
- Keeps the deterministic fake backend limited to explicit conformance tests;
  production configuration cannot select it.

## Compatibility

Existing repository configuration and Codex, Claude, and API routing remain
compatible. Pre-cutover repositories retain their established checkpoint
behavior. Transactional repositories receive the additive migration and keep
the fail-closed startup and one-writer guarantees introduced in 1.8.33.
Container, microVM, Kubernetes, and remote-worker backends remain out of scope.
