# Orka 1.8.36

Orka 1.8.36 defines the first stable provider-neutral contract for external
engineering services.

## What changed

- Adds versioned capabilities for Jira-style issue inventory, dependencies,
  status transitions, and comments, plus GitHub-style pull requests, CI,
  approvals, comments, merge requests, and merge receipts.
- Rejects provider-specific payload fields through strict, typed,
  per-capability normalized schemas before evidence can enter controller state.
- Binds reads, pages, mutation intents, acknowledgements, and reconciliation to
  immutable repository, adapter, request, operation, and external-object
  identities.
- Requires complete pagination proofs and exact item-identity digests for every
  collection read.
- Persists mutation intent before provider I/O, prevents concurrent duplicate
  submissions, and separates completed, rejected, rate-limited, ambiguous, and
  unacknowledged outcomes.
- Makes every claimed mutation reconcilable across process restart, rejects
  reconciliation-key collisions, and permits rate-limit retry only for the
  same exact intent after its durable deadline.
- Includes credential-free conformance fixtures for all 13 currently mapped
  Jira and GitHub capabilities.

## Trust boundary

The bundled coordinator and deterministic adapter are a conformance reference,
not production Jira or GitHub routing. Adapters cannot schedule work, reserve
budget, choose dependencies, authorize merges, or weaken repository policy.
Credentials and raw provider payloads never cross the adapter boundary.

The reference intent store supports cooperating POSIX processes on a local
filesystem that honors advisory locks and durable file/directory fsync. A
distributed host must provide equivalent atomic-claim and durable-commit
semantics.

## Compatibility

Existing Jira and GitHub clients remain authoritative. This release maps their
current behavior to the contract without routing production operations through
the new boundary or adding another provider.
