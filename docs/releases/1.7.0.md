# Orka 1.7.0

Orka 1.7.0 gives native gateway reservations an evidence-bound reconciliation
path, so a sprint ticket whose worker hit a provider read timeout can be
restarted after the operator confirms the request never reached the provider.

## Gateway reservation reconciliation

- `reconcile-reservations` now accepts `not-found` entries for reservations
  written by the controller-owned Claude or Codex gateway, which never have a
  `.llm-runs` marker.
- Acceptance requires the ticket's controller launch record for that exact
  invocation, a terminal execution record written after the reservation, and
  the controller's liveness check proving the execution unit is gone.
  Cooperative units also need a closed gateway and no surviving worker group.
- Live or unknown units, mismatched runs or tickets, completed outcomes, empty
  evidence, manifests outside the repository, duplicates, non-gateway
  reservations without a run marker, and gateway reservations that also have a
  run marker remain refused.
- Each release writes a durable audit record under
  `.orchestration/.llm-usage/gateway-reconciliations/` before touching the
  ledger. Re-applying the same manifest is idempotent.
- `reservation-migration-plan` labels each entry's `source` and lists
  reservations neither path can accept under `excluded` with the reason.
- New reservations record `origin` (`api-run`, `native-gateway`,
  `codex-gateway`, or `provider-batch`). Existing ledgers need no migration;
  unmarked gateway-shaped reservations are recognized conservatively.
- `restart-ticket` no longer reports outstanding reservations for a ticket once
  its gateway reservations are reconciled.

## Per-reservation gateway evidence

- `reservation-migration-plan` no longer fills in an outcome for gateway entries.
  `outcome` and `evidence` are left empty, so applying an unedited plan is
  refused. Each gateway entry now includes a `request` block (ticket, provider,
  model, `reserved_at`, projected cost, stop reason) and `evidence_must_name`.
- Gateway evidence must name its own reservation: either the reservation id or
  the UTC request minute (`YYYY-MM-DD` plus `HH:MM`). Evidence is also refused if
  it contains template or placeholder text (`<...>`, `{{`, `...`, `TODO`, `TBD`,
  `n/a`, `same as above`, and similar), is shorter than 24 characters, or has
  fewer than three words. The same sentence can cover several reservations only
  if it names each one. A range such as `22:30-22:50` names none of them. A
  replay of the sprint 65 ledger showed why this matters: evidence pasted onto
  every entry would have released BL-1762's 22:49 reservation, which nobody had
  looked up.
- API run entries (`source: api-run`) keep their existing evidence rules.

## Completed gateway requests

- `reconcile-reservations` now accepts a `completed` outcome for gateway
  reservations. This replaces the earlier behavior, which refused completed
  outcomes. A `completed` entry needs the provider `response_id` and integer
  `input_tokens`, `cache_write_tokens`, `cache_read_tokens`, and `output_tokens`.
  It must pass the same controller execution checks and evidence rules as
  `not-found`.
- Usage is priced with the configured `llm.pricing` entry for the reservation's
  model and settled as a normal ledger `usage` event. The audit record stores the
  response id, usage, cost, and whether the cost exceeded the reservation.
- A cost above the reservation's projected worst case is refused by default. The
  reservation stays open and keeps counting its projection, so no usage is lost.
  `--accept-cost-above-reservation RESERVATION_ID` settles the actual cost for
  that one reservation.
- Zero usage, `not-found` entries that carry usage fields, and a response id
  that is reused within the manifest or already settled another reservation are
  refused.

## Restart refusal names blocking reservations

- When `restart-ticket` refuses because of outstanding reservations, it now lists
  each blocking reservation id with its run id, projected cost, reservation time,
  and origin.
- The restart-allowance example in `docs/sprint-controller.md` now uses shell
  variables instead of angle-bracket placeholders, which the shell reads as
  redirects. It runs `restart-ticket` as the runtime user from inside the
  repository (`cd "$REPO" && sudo "$HELPER" issue-restart ... | sudo -u
  "$RUNTIME_USER" python3 .../sprint-controller.py restart-ticket ...`), so the
  controller no longer looks for `/root/.orchestration/config.yaml`.

## Test reliability

- In `sprint-controller.test.sh`, the "confirmed process absence permits
  automatic requeue" case now waits, for at most 30 seconds, until the
  controller's liveness check reports the killed worker's execution unit absent.
  Before, it requeued while the supervisor could still be writing its terminal
  record.

## Configured review gates are required

- The review ledger now requires every configured `gates:` entry it owns
  (`code-review`, `security-review`), not only gates that received a permit. A
  generation that issued only a security permit can no longer clear without a
  code review.
- A missing or empty `gates:` key fails closed to both gates, matching
  `templates/config.yaml`. The list is read through the shared configuration
  parser, so block, one-line, and Prettier-wrapped lists agree.
- Code review is always required. A `gates:` list that omits it, or names only
  gates the ledger does not own, cannot remove the independent code review;
  only `security-review` is optional.
- New `record-security-gate <pr> --head <full-sha> --decision <file>` binds the
  `orchestration-engine.py security-gate` output to the current generation and
  exact head. A configured security gate is waived only by a `required: false`
  decision; no decision, any `required: true` decision, or an issued security
  permit keeps it required.
- Decisions do not carry into repair or rebind generations; record one per head.
- `complete-repair-review` recomputes the required set, so existing ledgers that
  stored a shorter set on a pending repair are corrected on read.

## Abbreviated repair heads

- `record-repair` resolves the report `head` with `git rev-parse --verify` and
  stores the full commit id. A head that does not resolve to exactly one commit
  is refused. The report schema is unchanged.
- `record` compares resolved full ids. A ledger that already stored an
  abbreviation accepts its full expansion only when git resolves the
  abbreviation unambiguously to that commit.
- New `correct-repair-head <pr> --head <full-sha> --reason "..."` rewrites a
  pending attempt's abbreviation to that same expansion with an audit entry. It
  refuses any other commit, a completed attempt, or an already-full head.

## Completed API review permits

- `complete-review` after an API run that already completed its permit now
  returns the existing unconsumed receipt with `already_completed: true` when
  the role, head, and result digest are identical.
- A different result digest, or a recorded, cancelled, or superseded permit,
  is still refused with a specific message.
- `/gate` and the Codex gate skill state that `complete-review` is for desktop
  reviewers; API runs go straight to `record`.
- `complete-review` refuses a permit that an API run started but has not
  completed, so a desktop completion cannot mint a receipt for an API review.

## Reviewing a PR head outside the checkout

- The local `HEAD` binding for review permits is unchanged. Its error now names
  the actual repository `HEAD` and the review worktree command.
- `/gate`, the Codex gate skill, and the review-loop guide document reviewing
  from `git worktree add --detach <path> <sha>` and removing it afterwards.
  Linked worktrees share the same review ledger and canonical config.

## Reviewer run reconciliation releases the review permit

- Reviewer run markers now bind their started review permit by PR, role, exact
  head, ledger directory, logical review id, and a token digest and prefix; the
  token itself is not stored.
- `api_agent.py reconcile` cancels that permit after the reservation is released
  or settled, for both `not-found` and `completed` outcomes. A completed
  reconciliation never yields a PASS: the review must be re-run.
- A money reconciliation failure leaves the permit untouched. Already cancelled,
  superseded, or completed permits are reported without failing reconciliation.
  `reconcile-reservations` cancels bound permits the same way.
- New `review-ledger.py cancel-permit <pr> --phase-permit <token> --reason
  <text>` releases a started permit, including one from a run marker written
  before the binding. It refuses while a usage reservation for the permit's run
  or logical review is open, and refuses unstarted, completed, cancelled, or
  superseded permits. It records the reason and never creates a receipt.
- `permit-review` refusals for a started review now name the permit prefix, the
  run, and both recovery commands.

## Repair briefs keep every gate's explanation

- Components now store `findings_by_gate`, so code-review and security-review
  findings on the same normalized component no longer overwrite each other.
- `repair-brief` and `handoff` print each open gate's title and explanation
  labelled by gate in stable order. Direct records, staged repair finalization,
  concurrent-review migration, and `alias` all preserve per-gate details.
- Ledgers that only carry the legacy single `finding` still render unchanged.

## Review budgets that fit a real review

- Repository configuration can raise `max_usd_per_design_phase`,
  `max_usd_per_code_review_phase`, and `max_usd_per_security_review_phase` up
  to a $10 hard cap, equal to the compiled `max_usd_per_run`. Defaults stay at
  $5. Implementation, run, ticket, sprint, pause, and run-count ceilings still
  cannot be raised.
- Only the $5 design default can transfer to implementation after design
  approval, so a raised design phase cannot enlarge implementation.
- New `llm.budgets.max_output_tokens_per_review_turn` (default 8192, never
  above `max_output_tokens_per_turn`) bounds the output each reviewer turn
  submits and reserves. A 32768-token allowance previously reserved about
  $2.64 per request and refused $5 reviews after about $2.40 of work.
- When a reviewer's next tool continuation is refused by a dollar ceiling, or
  `max_tool_rounds` is reached, Orka sends one final tool-free verdict request
  capped at the new `llm.budgets.final_verdict_output_tokens` (default 4096).
  It uses normal admission and validation, and records `final_turn` (`budget`
  or `max_tool_rounds`) in the run state and result. A forced FAIL receives a
  completion receipt; a forced PASS is not authoritative, so the run ends
  `budget_blocked` with no receipt and the permit is released for a fresh
  review. If the request does not fit, or it returns tool calls, the run stays
  `budget_blocked`.
- The first reviewer request carries an `ORKA BUDGET NOTE` with the phase
  ceiling, spend so far, remaining capacity, per-turn output reservation, and
  tool-round limit.

## Budget values above hard caps are reported

- `orchestration-engine.py validate-config` prints a `WARNING` to stderr for
  each `llm.budgets` value above its hard cap, naming the value Orka enforces.
  Validation still succeeds.
- `api_agent.budget_cap_violations(config)` returns the same findings as
  `key`, `configured`, `effective`, and `cap` strings.

## Scoped open-reservation counts in usage reports

- `api_agent.py report` counts open reservations with the same role, model,
  provider, ticket, sprint, and window filters as its usage groups.
- Reservations outside the filters appear only as a separate ledger-wide count
  (`open_reservations_ledger_wide` in JSON).

## CI-verified review checks

- Reviewer checks accept a new `ci_verified` status for checks satisfied by CI
  on the exact reviewed commit, such as database suites a repository forbids
  running locally. It needs no blocking finding.
- `ci_verified` requires `evidence` with exactly `ci_check` (the CI check-run
  name) and `head_sha` (the full reviewed head). Missing, empty, abbreviated,
  or mixed-head evidence is rejected, and `evidence` is refused on every other
  status. `fail` and `not_run` still require a blocking finding.
- `validate-review --head` and `--ci-evidence` add an optional fail-closed
  cross-check: the cited run must exist, be `completed`, and conclude
  `success` at the reviewed head. Structural validation stays unchanged for
  existing callers.
- `context_pipeline.py payload --ci-evidence <file> --review-head <sha>` embeds
  a normalized, 64-run-bounded summary (name, status, conclusion, head SHA,
  URL) of exact-head check runs, refusing evidence for any other commit.
  `--fetch-ci-evidence` captures it through `gh` only when explicitly requested.
- Reviewer briefs, `docs/reviewer-output.md`, `/gate`, and the Codex `gate-pr`
  skill explain when `ci_verified` is allowed and how to capture CI evidence.
- `review-ledger.py record` refuses any result with a `ci_verified` check
  unless `--ci-evidence` for the exact `--head` confirms the cited run passed.
  `complete-review` and API reviewer completion reject `ci_verified` evidence
  citing a different head.

## Prettier-formatted configuration lists

- The engine parser now accepts flow lists that Prettier moves onto the line
  after their key (`allowed_tools:` then an indented `[read_file, search]`) or
  wraps across lines, including trailing commas, comments inside the list, and
  quoted items containing `,`, `[`, `]`, or `#`. Each form parses exactly like
  the one-line list.
- Quoted flow items containing commas are no longer split (for example
  `security_required_when: ['a, b']`), and a trailing comma no longer adds an
  empty item.
- The LLM route reader, Jira field reader, `lib-config.sh` `orch_list`, the
  sprint controller's status lists, and the Jira inventory priority order now
  read lists through the same parser. Flow lists there previously produced a
  refusal or a silent default.
- Unsupported YAML now fails with its line number and a `hint:` naming the
  supported form: an unterminated `[`, non-empty flow mappings, nested flow
  lists, block scalars, multi-line values, and text after a closing `]`. A
  one-line `key: [x` or `key: {a: 1}` used to be read as a string. `key: {}` is
  now an empty map.
- Valid block lists and one-line flow lists need no changes.
